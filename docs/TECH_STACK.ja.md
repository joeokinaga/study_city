## Flutter Web

同じコードベースでWeb・iOS・Androidをターゲットにできるため採用。現在はWebアプリとして公開しているが、将来モバイルアプリをリリースする際も追加フレームワークが不要。ReactでモバイルアプリをつくるにはReact Nativeを別途導入する必要がある。DartのStrong modeにより、SM2スケジュールやEXP/コインのデータモデルのバグを実行時ではなくコンパイル時に検出できる点も利点。

トレードオフ：Flutter WebはReactやVueと比べて初回ロード時のバンドルサイズが大きく、SEOも弱い。ただしこのアプリではどちらも問題にならない。ユーザーはログイン後にコンテンツを見るためSEOは不要で、バンドルサイズもランディングページではなく繰り返し使うツールとして許容できる範囲。

## Firebase

Auth・Firestore・Cloud Messagingを1つのSDKで利用できる点を評価して採用。個人開発でカスタムバックエンドサーバーを管理すると、SM2・報酬・都市建設といったコアロジックへの時間が削られる。FirestoreのリアルタイムストリームはアプリのライブアップデートUI（科目一覧、復習キュー）と自然にマッピングできる。

トレードオフ：Firestoreは複合インデックスなしで複数フィールドのフィルタリングができない。`StudySessionRepository`の日付範囲クエリはこの制限を回避するため、ユーザーの全セッションを取得してからDart側でフィルタリングしている。ユーザー1人のセッション数は多くても数百件程度のため全件取得でも問題ないが、データ規模が大きくなる場合はPostgreSQLなどRDBへの移行が適切。

## flutter_riverpod（ChangeNotifierProvider）

ウィジェットツリー外（`BuildContext`不要）でプロバイダーを読み取れる点を評価してProviderより採用。ViewModelがFlutter自体に依存しなくなるため、ユニットテストがシンプルになる：モックリポジトリを注入し、純粋なDartコードだけで状態遷移を検証できる。

`AsyncNotifier`へのマイグレーションは行わなかった。アプリの非同期処理（Firestoreの読み書き）は常にユーザーの明示的操作をトリガーとしており、ウィジェットのマウント時には発生しないため、`ChangeNotifier`で十分だった。

## go_router

`redirect`コールバックによる宣言的ルーティングのために採用。認証ガードが各画面に散在せず`router.dart`一箇所にまとまる。追加実装なしでDeepLinkとブラウザの戻るボタンが正しく動作する。

## fl_chart

統計画面のバーチャートとパイチャートのレンダリングに採用。Web向けに軽量で、学習履歴の可視化に必要なカスタムスタイリング（科目ごとの色分け）をサポートしている。

## wakelock_plus

学習セッション中に画面がスリープするのを防ぐ。シンプルなAPIを持つ単一目的のパッケージ。
